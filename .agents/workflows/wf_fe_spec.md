## EXECUTION CONTRACT

Steps 1→6 sequential. Each step: validate → if fail → retry 2x → **FALLBACK** (mark `⚠️ PARTIAL`, skip dependents, log in summary).

**DO NOT:** skip contract load (Step 1), skip skill rule loading (Step 1), generate tasks without contract, create tasks for `visibility: internal` fields, skip human review gate for HIGH complexity tasks.

**Input**: Change name (kebab-case).

**Entry Modes**:
- **Mode A (Contract-Based)**: After `/wf_api_contract` generates `api_contract.md` — standard flow

- **Mode D (Frontend-Only)**: Standalone — user provides or creates `api_contract.md` manually

**Idempotency:** If `fe_tasks.md` exists → ask: **Overwrite** | **Merge** (default) | **Skip**. No response → Merge.

## STEP 1 — Load Context (Hierarchical Memory Strategy)

> **Memory Architecture**: 3-layer loading to minimize token usage.
> Layer 1 (Working Memory) loads first. Layer 2 lazy-loads on demand. Layer 3 only for fallback/contract-less mode.

### 1a. Detect Input Mode

Check `openspec/changes/<name>/`:

```
IF api_contract.md EXISTS:
  IF .memory/contract_state.md EXISTS → Mode C (Memory-Enriched)
  ELSE → Mode A (Contract-Based)
ELSE:
  IF design.md EXISTS → Mode B (Contract-Less)
  ELSE → Mode D (ask user for manual contract)
```

### 1b. Load Layer 1 — Working Memory (Always Load)

| Source | Tokens | Required | Notes |
|--------|--------|----------|-------|
| `api_contract.md` | ~2-4K | Mode A/C/D | Source of truth for API shape |
| `ui_design_spec.md` | ~3-5K | Mode A/C | Source of truth for UI layout, wireframe, interactions |
| `.memory/contract_state.md` | ~100 | Mode C only | Status, drift, consumers, gate |
| `fe_tasks.md` (if exists) | ~1-2K | Merge mode | Previous output for delta merge |
| `openspec/specs/design-guidelines.md` | ~1-2K | Always | Shared design tokens, component conventions, responsive rules |

> ⚠️ `ui_design_spec.md` is generated by `/wf_api_contract` Step 2.5. If missing → WARN `"⚠️ No ui_design_spec.md found. Tasks will lack design context. Run /wf_api_contract first."` → continue with degraded quality.

### 1b-2. Load Upstream Context (Design Grounding)

| Source | Path | Tokens | Load When | Purpose |
|--------|------|--------|-----------|---------|
| `brainstorm_notes.md` | `openspec/changes/<name>/brainstorm_notes.md` | ~500 | Optional | Design direction, selected approach |
| `pre_openspec.md` | `openspec/changes/<name>/pre_openspec.md` | ~300 | Optional | FR list, feature type, scope |
| `business_analysis.md` | `openspec/research/<name>/business_analysis.md` | ~500 | Optional | Use cases for context |

**Lazy load rules:**
- `brainstorm_notes.md`: Read `## Selected Direction` only
- `pre_openspec.md`: Read `> **Type**:` only
- `business_analysis.md`: Read `## 2. Use Cases` section headers only (for UC reference in tasks)

**Mode B (Contract-Less) alternative:**
| Source | Tokens | Notes |
|--------|--------|-------|
| `design.md` (endpoint sections only) | ~1-2K | Extract HTTP endpoints + DTOs |
| `srs.md` (error codes + validation) | ~500 | Extract error specs + validation rules |

> ⚠️ **Mode B Design Fallback**: `ui_design_spec.md` will NOT exist (it’s generated by `/wf_api_contract`). In Mode B:
> - PAGE tasks use **basic MUI layout patterns** from `design-guidelines.md` §4 (no wireframe refs)
> - States defined minimally: loading (spinner), error (alert), empty (text), success (toast)
> - Recommend running `/wf_api_contract <name>` first to get full design context

### 1c. Verify Contract (Mode A/C/D)

**Validate contract:**
- Has `<!-- contract-version: -->` header
- Has `## Endpoints` section with ≥1 endpoint
- Has `## Response Wrapper` section
- All endpoints have Request + Response + Errors

If validation fails → advise:
```
⚠️ api_contract.md invalid or incomplete.
Options:
  1. Run /wf_api_contract <name> to regenerate
  2. Fix manually using template: skills/api-contract-generator/templates/api_contract.template.md
  3. Switch to Contract-Less mode (type "contract-less")
```

### 1d. Check Memory Status (Mode C — Bonus Context)

Read `.memory/contract_state.md`:
- `backend_status` → if `implemented` → contract is validated against code
- `drift_detected` → if `true` → WARN user, show drift log
- `consumers` → check `web` platform status
- `gate_rules` → informational only (fe_spec doesn't gate)

> This metadata enriches task generation: if backend is implemented, service layer can target real API immediately (skip mock-first approach).

### 1e. Load Layer 2 — Short-Term Memory (Lazy Load)

Load **on demand** during Step 3 task generation:

| Source | Tokens | Load When |
|--------|--------|-----------|
| `base_knowledge/frontend/react_patterns.md` | ~500 | Generating component tasks |
| `base_knowledge/frontend/mui_conventions.md` | ~400 | Generating theme/styling tasks |
| `base_knowledge/frontend/routing_conventions.md` | ~300 | Generating route tasks |
| `vercel-react-best-practices` SKILL.md (index) | ~150 | Generating any code task |
| `ui-review` SKILL.md (index) | ~90 | Generating review task |
| `design-taste-frontend` SKILL.md (index) | ~150 | Generating component/page tasks |
| `ui-ux-designer` SKILL.md (index) | ~100 | Generating design review task |

> ⚠️ DO NOT load full rule files (`rules/*.md`). Only load specific rules in Step 3 when generating tasks.

### 1f. Load Layer 3 — Long-Term Memory (Fallback Only)

> Only loaded in **Contract-Less mode** (Mode B) or when Layer 1 is insufficient.

| Source | Tokens | Load When |
|--------|--------|-----------|
| `design.md` (full) | ~3-5K | Mode B — no contract available |
| `srs.md` (full) | ~3-5K | Mode B — need error codes, validation rules |
| OpenSpec context files | Never | Too much context, not relevant for FE |

### 1g. Load Frontend Source Context

Scan project structure — **DO NOT** read all files, use targeted discovery:

```
src/
├── @auth/           → Auth patterns (authApi.ts, useUser.tsx, authRoles.ts)
├── app/             → Route structure (import.meta.glob pattern)
├── configs/         → Route config patterns
├── hooks/           → Custom hook patterns
├── services/        → Service layer patterns (if exists)
├── utils/           → Utility patterns (api.ts → HTTP client)
└── theme/           → MUI theme config
```

**Strategy**: Use `grep_search` + `list_dir` first. `view_file` only for pattern-critical files.

**Validate:** Input mode determined, required context loaded per mode, skills indexed.

## STEP 2 — Classify Frontend Change

Read `api_contract.md` endpoints + `## State Contracts` → classify what needs to be built:

| Type | Criteria | Example |
|------|----------|---------|
| `PAGE` | New route/page component needed | Admin user management page |
| `COMPONENT` | Reusable UI component needed | DataTable with server-side pagination |
| `HOOK` | Custom React hook needed | `useAuth`, `usePagination` |
| `SERVICE` | API integration service layer needed | Auth service, CRUD service |
| `STATE` | State management change needed | Auth context update |
| `THEME` | Theming/styling change needed | Dark mode support |
| `ANIMATION` | Route/component transition needed | View transitions between pages |
| `DESIGN_REVIEW` | Pre-implementation design verification | Wireframe compliance check |

**Output**: List of change types with rationale.

**Reference**: Use `ui_design_spec.md` → Screen Inventory for page/component identification. Use `web-design-guidelines` source for UI complexity determination.

## STEP 3 — Generate Frontend Tasks

For each classified change type, generate tasks following this structure:

```markdown
## Frontend Tasks: <change-name>

<!-- generated-by: wf_fe_spec -->
<!-- contract-version: {{from api_contract.md}} -->
<!-- design-version: {{from ui_design_spec.md}} -->
<!-- design-guidelines-ref: openspec/specs/design-guidelines.md -->
<!-- complexity: LOW | MEDIUM | HIGH -->
<!-- estimated-tasks: N -->

### Task 0: Design Verification (Pre-Implementation)
- **Type**: DESIGN_REVIEW
- **Input**: `ui_design_spec.md` + `openspec/specs/design-guidelines.md`
- **Checklist**:
  - [ ] Wireframes cover all screens in Screen Inventory
  - [ ] Component hierarchy matches screen inventory
  - [ ] All interaction states defined (loading, empty, error, success)
  - [ ] Responsive spec complete for all screens
  - [ ] Design guidelines compliance checked
  - [ ] No [OPEN] design questions remain unresolved
- **Output**: Design compliance verdict (PASS / NEEDS REVISION)
- **Gate**: If NEEDS REVISION → STOP, fix ui_design_spec.md before continuing

### Task 1: TypeScript Types (from Contract)
- **File**: `src/types/<feature>.types.ts` | Action: [NEW]
- **Contract Source**: `api_contract.md` → Shared Types + endpoint Response types
- **Visibility Rule**: Only `visibility: public` fields → TypeScript interfaces
- **Pattern**: Follow existing `src/@auth/` type patterns

### Task 2: API Service Layer
- **File**: `src/services/<feature>.service.ts` | Action: [NEW]
- **Contract Source**: `api_contract.md` → Endpoints section
- **Dual-Mode**: Generate with `VITE_USE_MOCK_API` toggle
  ```typescript
  // Pattern: Dual-mode service
  const useMock = import.meta.env.VITE_USE_MOCK_API === 'true';
  
  export const featureService = useMock 
    ? mockFeatureService  // from mock/ directory
    : realFeatureService; // from real API calls
  ```
- **Response Unwrap**: Service MUST unwrap `ApiResponse<T>` → return `T` directly
- **Error Handling**: Map contract error codes → throw typed errors
- **Skills Applied**:
  - `vercel-react-best-practices` → `async-parallel` (Promise.all for independent calls)
  - `vercel-react-best-practices` → `client-swr-dedup` (SWR/TanStack Query dedup)

### Task 3: Custom Hook
- **File**: `src/hooks/use<Feature>.ts` | Action: [NEW]
- **Depends**: Task 2 (service layer)
- **State Shape**: From `api_contract.md` → State Contracts section
- **Pattern**: Follow `src/@auth/useUser.tsx` pattern
- **Skills Applied**:
  - `vercel-react-best-practices` → `rerender-*` rules (memo, derived state)

### Task 4: Page Component
- **File**: `src/app/<route>/page.tsx` | Action: [NEW] or [MODIFY]
- **Route**: Auto-register via `import.meta.glob` pattern
- **Design Ref**: `ui_design_spec.md` → Screen: "<Screen Name>" → Wireframe #N
- **Layout**: <layout-pattern> from design-guidelines §4, specific wireframe spec
- **States** (MANDATORY — from `ui_design_spec.md` → Interaction Spec):
  - Loading: <skeleton description matching wireframe shape>
  - Empty: <illustration + message + CTA>
  - Error: <error banner/inline + retry action>
  - Success: <toast/notification>
- **Responsive** (from `ui_design_spec.md` → Responsive Spec):
  - Desktop (≥1024): <layout description>
  - Tablet (768-1023): <collapse rules>
  - Mobile (<768): <mobile-specific patterns>
- **Interactions** (from `ui_design_spec.md` → Interaction Spec):
  - <key interactions with triggers, feedback, duration>
- **Components** (from `ui_design_spec.md` → Component Hierarchy):
  - <list of child components used in this page>
- **Data**: From Task 3 hook
- **Skills Applied**:
  - `vercel-react-view-transitions` → `<ViewTransition>` for page enter/exit
  - `vercel-react-best-practices` → `bundle-dynamic-imports` (lazy loading)
  - `vercel-react-best-practices` → `rendering-*` rules
  - `design-taste-frontend` → layout variance, typography, color calibration
  - `ui-ux-designer` → interaction design, state management, accessibility

### Task 5: Route Registration
- **File**: `src/app/<route>/route.tsx` | Action: [NEW] or [MODIFY]
- **Pattern**: `CoreRouteItemType` from `@core/utils/CoreUtils`
- **Auth**: `settingsConfig.defaultAuth` or specific `authRoles`
- **Lazy**: `React.lazy()` for code splitting
- **Layout**: Config navbar/toolbar/footer display

### Task 6: Unit Tests
- **File**: `src/app/<route>/__tests__/<Feature>.test.tsx` | Action: [NEW]
- **Framework**: Vitest + JSDOM
- **Coverage**: Service layer + hook + component render
- **Skills Applied**:
  - `vercel-react-best-practices` → test patterns

### Task 7: UI Review Audit (Post-Implementation)
- **Type**: REVIEW (not code generation)
- **Skill**: `ui-review` → full checklist
- **Skill**: `web-design-guidelines` → fetch latest rules
- **Design Compliance**: Full audit checklist → see `wf_fe_apply` Step 5c for detailed checks
  - Brief summary: wireframe match, 4 states, component hierarchy, colors/typography/spacing, responsive, animation
- **Output**: `fe_review.md` with verdict
```

**Task Generation Rules**:
- Each task MUST reference its contract source section
- Each task MUST list applicable skill rules
- Tasks MUST be ordered by dependency (design review → types → service → hook → component → route → test → UI review)
- Each task MUST have a clear validation criteria
- Service tasks MUST generate dual-mode code (mock/real toggle)
- `[MODIFY]` actions MUST document what changes vs existing code
- **PAGE tasks MUST reference** `ui_design_spec.md` wireframe, interaction spec, and responsive spec
- **PAGE tasks MUST define** all 4 states: loading, empty, error, success
- **PAGE tasks MUST specify** responsive behavior for all breakpoints
- **PAGE tasks MUST list** child components from component hierarchy

## STEP 4 — Complexity Classification + Human Review Gate

### 4a. Auto-Classify Complexity

| Factor | LOW | MEDIUM | HIGH |
|--------|-----|--------|------|
| Endpoint count | 1-2 | 3-5 | 6+ |
| Nested components | 0-1 | 2-3 | 4+ |
| State management | Simple useState | Context/reducer | Cross-component + cache |
| Custom animations | None | Basic transitions | Complex choreography |
| Third-party libs | 0 | 1-2 | 3+ |
| Existing code impact | None (new) | 1-2 files modify | 3+ files modify |

**Score**: Count HIGH factors. ≥2 HIGH → task is `HIGH` complexity.

### 4b. Review Gate

- **`LOW`/`MEDIUM`**: Auto-proceed → generate `fe_tasks.md`
- **`HIGH`**: STOP → present tasks to user → wait for confirmation

```
═══════════════════════════════════════
⚠️ HIGH COMPLEXITY DETECTED
═══════════════════════════════════════
Change:    <name>
Tasks:     <N> tasks generated
Complexity: HIGH (factors: <list>)

Review the task list above.
Approve: type "approve" to proceed
Modify:  suggest changes
Cancel:  type "cancel" to abort
═══════════════════════════════════════
```

## STEP 5 — Validate Tasks

| Check | Condition |
|-------|-----------|
| Contract coverage | ALL contract endpoints have ≥1 service task |
| Type coverage | ALL contract Shared Types have TypeScript interface tasks |
| Error coverage | ALL contract error codes have frontend handling |
| Route consistency | Route pattern follows existing `src/app/` conventions |
| Visibility filter | NO `visibility: internal` fields in frontend type tasks |
| Skill coverage | Each code task has ≥1 applicable skill rule listed |
| Dependency order | Tasks ordered: design review → types → service → hook → component → route → test → UI review |
| Dual-mode | Service tasks include mock/real toggle pattern |
| **Design review task** | Task 0 (DESIGN_REVIEW) present and complete |
| **Design ref** | ALL PAGE tasks reference `ui_design_spec.md` wireframe section |
| **States defined** | ALL PAGE tasks have loading + empty + error + success states |
| **Responsive spec** | ALL PAGE tasks have responsive behavior for 3 breakpoints |
| **Interaction spec** | ALL PAGE tasks have interaction triggers + feedback defined |
| **Component hierarchy** | ALL PAGE tasks list child components from hierarchy |
| **Design guidelines ref** | `design-guidelines-ref` header present in metadata |

**Fail** → fix + re-validate (max 2).
